## 3.4.0 人脸复核表（含多选批量）

「人物与复核」页签下的二级子页签 **[待复核面孔]** 就是复核表；老分组
（已确认人物）原样不动。本次只加复核流程，删除逻辑、二次确认、待删
确认篓、语义找图、新版式布局一律没动。

### 单脸怎么认：主键 = 照片内容哈希 + 脸序号

- 单脸主键 `f<sha256 前 16 位>-<脸序号>`。同一份内容的多张重复照片
  共享同一张单脸身份，**只复核一次**（行内会写明「同内容照片 N 张」）。
- 脸序号按框中心**确定性**排序：先上后下（按行带），同一行再左到右；
  不用检测分数排，避免重扫后序号跳变、复核记录对不上人。
- 每条单脸记录保留：脸框、YuNet 检测分、与各人物/簇的相似度、128 维
  SFace 特征。特征落在独立的 `face_embed_cache.json`（可写目录下），
  重扫命中缓存直接复用，不重算；缓存带算法签名，算法或阈值一变就整体
  作废，绝不复用可能错位的旧框。

### 三张卡片与打分

| 卡片 | 判定 | 说明 |
|---|---|---|
| 建议 | 与某人相似度 ≥ 0.60 | 可直接采纳；卡片顶部有「一键采纳本页建议」 |
| 可疑 | 0.40–0.60 | 需要人再看一眼；前两名太接近时同展两个候选 |
| 未匹配 | 最高相似度 < 0.40 | 谁都不像，多半是陌生人或误检 |

- **打分不用组平均中心**，用组内已确认成员的最近邻（前 3 名均值）；
  头像用组内代表脸（检测分高、框大者）。
- **双候选降级**：Top1 与 Top2 差 < 0.06 时，即使 ≥ 0.60 也进「可疑」，
  并把两个候选与各自相似度一起显示。
- **单脸孤立簇**不会因为“跟自己相似”进建议：算分时先把自己排除，
  孤立簇只能按与其他组的最高分落到可疑或未匹配。
- 已忽略的脸在**聚类前**就剔除，不参与聚类，避免把两个簇桥接起来；
  重扫后也不会再出现在复核表里（照片本身不动）。

### 每行与全图

每行：复选框 · 裁剪小图 · 来源照片名与拍摄日期 · 建议人 + 相似度 ·
四个操作（采纳建议 / 分到其他人 / 新建人物 / 忽略这张脸）。裁剪小图是
**动态裁剪接口**（`/api/review/crop`，外扩留白，内容不贴边；四周留白边由前端 `.revcrop` 按当前主题给，深色下不刺眼）
配懒加载与分页（每卡片每页 6 行），扫描响应里不塞图片数据。点小图打开
全图，全图里带高亮框，四个操作直接在弹窗里做完，不用回列表。

### 多选批量（本版就有）

每行左侧复选框；每张卡片顶部「全选本页」；选中后出现吸顶批量条：
批量采纳建议 / 批量分到某人（弹人选）/ 批量忽略 / 清空选择。一次批量
操作在撤销记录里是**一条含多项快照的事务**，可整批撤销，也可事后单脸
再改。本版不做数字键 1–9、拖拽分配、按 P 搜人（下一版）。

### 撤销与本机数据文件

一个文件 `face_review.json`（可写目录下）存四块内容：人物、每张脸当前
状态、操作历史、迁移过来的旧名。复核操作只改归属，**绝不删照片**，也
绝不混用删照片的二次确认与待删篓。

- 任何一条记录都能撤销；撤销旧记录时若该脸后来又被改过，先返回 409 冲突
  并在界面提示「先处理最新记录」，可选择只撤销未冲突的部分，或明确选择
  整条强行覆盖——不会静默覆盖。
- 新建人物被撤销时，仅当该人物名下已无脸且没被改过名，才会清理这个空人物。
- 新人物用持久短标识 `p_xxxxxxxx`；自动簇 id 用锚点脸的哈希前缀
  `af_<哈希前缀>-<脸序号>`，不再用「人物 1/2/3」顺序编号。

### 人名存储与一次性迁移

人名从浏览器 localStorage 挪进 `face_review.json` 的人物记录。首次打开
（扫描后即可，迁移本身不依赖扫描成功）把 `photoTool.names.v1` 里的旧名
一次性导入 `legacy_names`，写 `migration.names_imported_at` 后就把旧键删掉、
另存一份 `photoTool.names.v1.backup`，之后再也不会从 localStorage 读人名。

- 本机已有的人工命名优先，不被浏览器旧名覆盖；
- 合并冲突以「已确认脸更多」的一方为准（旧名没有确认脸，计 0，所以人工
  命名天然胜出），冲突逐条记进 `migration.conflicts` 备查；
- 旧名按「簇 id → 锚点哈希前缀 → 当前扫描里成员照片有交集的旧分组 id」
  三档匹配，套到新建的人物上；人物被撤销清掉时会把旧名释放出来。

## 3.3.0 语义搜图（按意思找图）

### 本地模型：实际型号、体积与为什么不是 RN50

| 项 | 值 |
| --- | --- |
| 模型 | Chinese-CLIP **ViT-B/16 INT8（ONNX 量化版）** |
| 来源 | `Xenova/chinese-clip-vit-base-patch16` 的 `onnx/model_quantized.onnx` |
| 体积 | 190,842,404 字节（约 182 MiB）；词表 109,540 字节 |
| 向量维度 | 512 |
| 输入 | 图像 224×224（BICUBIC、CLIP 均值/方差归一化）；文本 BERT WordPiece、最多 52 token |
| 运行库 | `onnxruntime`（CPU），**没有用 `cv2.dnn`**（对 Transformer 算子兼容差） |

规格原本首选 RN50 INT8 ONNX。**实测结论（2026-10-31）：RN50 的 ONNX 版
确实不可用**——官方 `OFA-Sys/chinese-clip-rn50` 只发布 PyTorch 权重
`clip_cn_rn50.pt`（308 MB），HuggingFace 与 ModelScope 上都没有可直接
使用的 RN50 ONNX 发布版。因此改用当前体积最小的中文 CLIP INT8 ONNX
（ViT-B/16，190 MB）。**没有悄悄换回英文 MobileCLIP**：模型与词表都是
中文 CLIP，搜索词按中文 BERT 词表分词。

模型**绝不随主包捆绑**：只有用户第一次点「建立语义索引」且本地缺文件时
才下载，存到可写目录的 `models/`（程序目录可写时就是程序目录/models，
不可写时随 `app_paths` 回退到用户数据目录）。下载细节：

- 先写 `.part`，边下边报进度；完成后校验字节数与 SHA-256
  （模型 `a2c28493…a751`、词表 `45bbac6b…291c`），通过后 `os.replace`；
- 两个下载源：`huggingface.co` 与 `hf-mirror.com`，前一个失败自动试下一个；
- 失败会给出可读原因（HTTP 码 / 连接失败 / 校验失败），可直接重试；
- 下载中点「取消」会删掉 `.part`，不留半截文件。

### 索引：按内容 sha256、原子落盘、暂停续算

- 主键是 `scan.py` 已算好的**文件内容 sha256**，不是相对路径；同一内容的
  多份文件共享一条向量（演示集 25 张照片只有 22 条向量，就是因为有 3 张
  精确重复副本）。
- 单文件 `semantic/semantic_index.npz`（`app_paths` 可写目录下），文件头
  记 `model_id`、`dim`、`count`、更新时间；模型或维度不一致时判定
  `incompatible`，界面提示重建，不会拿旧向量硬算。
- 写入：同目录 `.tmp` + `fsync` + `os.replace`；索引线程每 64 张或每 10 秒
  落盘一次，暂停/取消/结束时立即落盘。实测暂停在 16/60 时，磁盘上正好
  16 条；重启进程后仍是 16 条，继续建索引只补算剩余 44 条。
- 查询只在当前扫描结果的 sha256 集合内计算；失效记录超过 20% 时做一次
  清理；删除成功后 `server.py` 立即调用 `forget_images()` 剔除对应向量
  （同一内容还有别的文件存在时保留）。
- 暂停只在批次边界生效（每批 8 张）：当前批已算完的向量会全部保存，
  不会白算半批；代价是点暂停后最多等一批（本机约 4~6 秒）。

### 搜索：复用原搜索框 + 关键词/语义切换

没有新增第二个搜索框。顶部搜索框右侧是「关键词 / 语义找图」胶囊；只有
切到语义找图才展开置信度滑块与「本次启用 API 精排」开关。关键词模式
仍是原来的文件名/人名/日期过滤，逻辑未动。

置信度不是直接把余弦当百分比。实测：25 张演示合成图 × 18 个中文词 =
450 个图文对，余弦分布为 **min 0.302 / p5 0.317 / 中位数 0.339 /
p95 0.390 / max 0.418**，动态范围只有约 0.116。因此做线性映射。
注意：以上分布来自合成演示图，真机照片的不相关图文余弦通常更低，
0.30 的下限在真机上可能偏严；没有真实照片分布前不擅自改常数，
真机实测时若标准档偏严，再把下限下调到 0.22~0.26 并重新验证：

```
score = (cos - 0.30) / (0.42 - 0.30) × 100   （截断到 0~100）
```

| --- | --- | --- | --- |

### Key 与隐私

- API Key 不写进代码、不写进 `settings.json`、不出现在前端 DOM 或日志。
  设置接口只返回 `has_key` 与掩码（如 `sk-****8f9a`）。

  绑定当前 Windows 账户）加密后存 `semantic/api_key.bin`；换 Windows

  不落明文文件（界面会明说）。
- 所有错误信息进界面前都过 `redact()`：先用真实 Key 做字面量替换，
  再过滤 `Authorization`、`Bearer`、`sk-…`、`AIza…` 形式的内容。

## 阶段三相对阶段二的修正（Argon 审查 P0/P1，全部已做并实测）

- **P0-1 连拍规则**：窗口由 1~15 秒改为 0~5 秒；簇内用三条条件区分
  「0 秒真连拍」与「0 秒修图变体」：文件名变体后缀（crop/edit/copy/filter/
  mmexport/wx_camera/compressed/bright 等）排除、众数分辨率一致性、灰度图排除；
  另要求与首帧 dHash 相似度 ≥ 80 且 ≥ 3 张成组。
  实测：0 秒高速连拍组（fastburst_001~004）检出；0 秒食物变体组
  （共用同一时间戳、文件名带变体后缀）不再误判为连拍。
  一点如实修正：棕褐变体不靠单图猜测——实测暖色食物场景 R-B 差达 77，
  单图棕褐启发式会误伤正常暖色照片；棕褐/黑白变体改由成对 RGB 均值差标注
  （有原图可对照时才可靠），见 P1-2。
- **P0-2 真实缩略图**：`scan.py` 为每张图输出 200×200 以内的 Base64 JPEG
  缩略图字段 `thumbnail`，画廊与 PK 台直接渲染真实画面，告别纯文字卡片。
- **P1-1 推荐规则**：多维评分——像素总面积 > EXIF 完整度 > 彩色优先 >
  文件名干净度 > 文件体积 > 文件名；生成器里裁切版不再 resize 放大回原尺寸
  （保持 768×576）。实测：食物组推荐保留的是母本原图 `base_food.jpg`。
- **P1-2 色彩差异**：dHash 先转灰度，对黑白/棕褐变体有 100% 盲区；补充 RGB
  通道均值差，dHash 100% 但 SHA 不同且均值差 ≥ 10 时标注
  「色彩变体（黑白/滤镜）」，并优先保留彩色原图。实测三对 100% 变体
  （海滩/黑白版差 19.3、公园/棕褐版差 58.8、裁切/滤镜版差 42.2）均已标注。
- **P1-3 安全删除闭环**：二次确认后的真正删除只走 `send2trash` 系统回收站；
  若 send2trash 不可用，则移入工具包内 `.trash_backup` 隔离文件夹并写删除日志；
  绝不直接 `os.remove` 彻底抹除；删除接口只接受本次扫描结果内的文件，
  且路径必须落在本次扫描根目录内（防目录穿越）。实测两条路径均已验证
  （见下方验证记录）。

## 人脸：诚实状态（必读）

- **Haar 级联只能做人脸检测（框出脸），做不了人脸聚类（认出同一个人）。**
  本工具绝不把 Haar 检出数冒充成认人结果。
- **真实人脸聚类必须走特征向量 + 聚类路线**（如 face_recognition、dlib、
  InsightFace 提取特征向量后用 DBSCAN 聚类）。`face_clustering.py` 已实现
  干净的预留接口：模型可用时走真实聚类，不可用时返回空并明说。
- **本机实测结论（2026-10-26，Linux VM）**：face_recognition、dlib、
  InsightFace、OpenCV、sklearn 均未安装；尝试用 pip 安装 face_recognition
  时，模型包（100.1 MB）与 dlib 源码（3.3 MB）下载成功，但 dlib 没有预编译轮子、
  必须从源码编译，编译依赖的 cmake 构建后端（30.2 MB）在本机 /tmp
  （tmpfs 仅 512 MB）上下载时报磁盘空间不足（Errno 28）而失败。
  因此本机真实人脸聚类不可用，界面显示的是**测试分组（非真实人脸识别）**，
  并在顶部横幅与报告里明说。
- **合成卡通测试图不能验证真实人脸聚类**：即使模型装好了，卡通画的脸
  也不是真实人脸，检不出是正常现象。真实人脸聚类必须用真实照片
  在真机环境验证（见下方「Windows 真机上还需实测」）。

## 遗留问题与诚实局限

1. **人脸真实聚类已接通，但只在公开测试人像上验证过**：YuNet+SFace
   路线与模型文件已随工具包提供（见上 v3.1.0 历史补丁 5），Lena/Obama
   公开测试人像上聚类正确；但尚未用用户真实照片验证（按规矩不能拿
   用户照片做测试），50~200 张真实照片小文件夹试跑须在用户 Windows
   真机上做；用户机器还需另装 opencv-python（不强制，随工具包注释说明）。
2. **Windows 真机上还需你实测**：`start.bat` 双击启动、缺依赖自动安装、
   失败时 pause 不闪退；`app_native.py` 的 pywebview 原生窗口与
   Chrome/Edge `--app` 回退（含“浏览器已在后台运行导致进程秒退/常驻”
   两种情形）、点“停止服务”后窗口是否真的关闭；选文件夹子进程弹窗；
   中文路径与中文文件夹名扫描、系统回收站路径（Windows 回收站）、
   跨盘文件是否进源盘回收站、程序装在 Program Files 时的可写目录回退；
   大图库（几千张）真浏览器下的滚动与加载更多体感、扫描耗时、
   深色/高分屏显示效果。
   本机 Linux 环境无法代替 Windows 真机验证，以上均标为「须真机实测」。
3. **大图库性能（残留）**：画廊 DOM 分页与动态缩略图接口已做（补丁 2），
   但扫描 JSON 本身仍内嵌每张图的 Base64 缩略图，实测 300 张约 2.9MB，
   几千张时首次下载约 30MB 级、加载变慢；超大图库建议分文件夹扫描，
   后续可加 `thumbs=0` 选项让扫描结果不内嵌缩略图（前端已全走
   /api/thumb，具备改造条件，本次未改以免动回归基线）。
4. **连拍分辨率众数过滤**：若某台设备连拍帧分辨率本身不一致（如混用
   拍照模式），众数过滤可能拆散该组；此时画廊仍可按时间看到这些照片，
   只是不进连拍保护组。
5. **搜索的地点/标签**：照片本身无地点/标签字段时不虚构，目前靠文件名、
   人物备注与拍摄日期匹配；后续若接入 EXIF GPS 再扩展。
6. **Pillow 版本提示**：旧版 Pillow 会在终端打印 `getdata` 弃用警告，
   不影响功能，可忽略；新版 Pillow 已改用新接口的后续版本可消除警告。
7. **本工具包不含用户真实照片**：演示图全部为程序现场绘制的合成图；
   扫描、删除验证均只用合成测试文件。
8. **3.3.0 语义搜图**：模型、索引与 API 精排的实测记录、尚未在 Windows
   真机验证的项，见上方「3.3.0 仍需 Windows 真机实测的清单」；真实照片

## 安全承诺

- 扫描只读：`scan.py` 不写被扫描文件夹、不删除、不移动任何文件。
- 删除只走回收站或隔离区，且只在用户二次确认后执行；删除接口拒绝
  本次扫描结果之外的文件与根目录之外的路径。
- 服务只监听本机回环地址，不对外公开分享。默认不上传任何照片；只有你
  本次勾选 API 精排时，才会把本地前 20 张候选的 200×200 低清拼图与搜索
  词发给所选厂商，原图与完整路径始终不出本机。
- 语义模型只在首次建立索引时从 HuggingFace / hf-mirror 下载并校验
  SHA-256；不做后台静默更新。
